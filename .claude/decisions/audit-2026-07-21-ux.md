# UX Audit: FitApp (NovaFit) — Full Flow Review
Date: 2026-07-21
Auditor: @ux-auditor (read-only pass — no source modified)
Scope: Onboarding · Daily habit loop · Social engagement loop · Mobile navigation · Retention mechanics

---

## Executive Summary

The product is in far better shape than a typical pre-release fitness app: onboarding has a real "aha moment" (the `your-numbers` reveal), the daily loop auto-saves, and every social list view has proper loading/empty/error states with converting CTAs. The single biggest problem is **retention has no outbound arm** — the streak-at-risk warning and all notifications only fire *while the user is already inside the app*, so nothing pulls a lapsing user back tomorrow. The highest-leverage fix is a scheduled "log today to keep your N-day streak" reminder (push/email) driven off the existing streak + `atRisk` logic. Second-order concern: the daily loop closes on a silent 16px save icon with no reward beat, which wastes the most motivating moment in the app.

---

## Section-by-Section Findings

### 1. Onboarding & First Value

**Finding:** Onboarding is genuinely strong. Flow is `register` (name/email/password + goal picker) → `/onboarding/carousel` (2 slides) → `/onboarding/biometrics` (height/weight/age/gender/activity with a **live TDEE estimate** computed client-side as you type, `onboarding-biometrics.component.ts:72`) → `/onboarding/your-numbers` (dramatic TDEE/BMR/BMI/target reveal + "Start your first workout" / "Log your first meal" CTAs). Value is delivered in ~4 steps and the numbers reveal is a real payoff moment.
**Impact:** Working well.
**Fix:** None required. Protect this flow.

**Finding:** The goal picker on register (`register.component.ts:18`) offers four options but `improve_fitness` silently maps to `apiValue: 'maintain'`. The user picks "Improve fitness 🏃" and the whole downstream calorie math treats them as maintenance. It is an invisible bait-and-switch on the one input that personalizes their numbers.
**Impact:** Medium.
**Fix:** Either drop the fourth option until the API supports it, or map "Improve fitness" to a distinct calorie strategy. Do not present a goal that the engine cannot honor.

**Finding:** Biometrics collects `dietaryPreference` (no-restriction / vegetarian / vegan / high-protein, `onboarding-biometrics.component.ts:120`) but this never resurfaces — the AI meal analyzer and nutrition suggestions don't appear to consume it. Asking for input you never use erodes trust and lengthens onboarding for nothing.
**Impact:** Low.
**Fix:** Feed `dietaryPreference` into the meal-analyzer/AI prompt context, or remove the field from onboarding.

**Finding:** `your-numbers-reveal.component.html:6` exposes `Skip to dashboard` as a raw `<a href="/user-dashboard">` (full page reload, not router navigation). Escape hatch is good; the implementation drops SPA state.
**Impact:** Low.
**Fix:** Use `routerLink` instead of `href`.

### 2. Daily Core Loop

**Finding:** The daily tracker (`daily-user-data.component.html`) is low-friction and well-designed: one screen, auto-save (`autoSaveStatus` badge), quick-adjust chips (+200/+100/−100 kcal, +500ml water, +1000 steps), a saved-meal picker with search, an **undo last meal** affordance, and inline AI meal analysis. Logging a full day is a handful of taps. This is the right altitude.
**Impact:** Working well.

**Finding:** The loop has **no closing beat / reward.** Completion is signaled only by a ~16px `check_circle` "saved" icon in the control bar (`daily-user-data.component.html:75-92`). There is no toast, no celebration, no "day complete" moment when a user hits their calorie target, water goal, or step goal. The most dopamine-rich instant in a habit app is silently swallowed. (Confirmed: only `daily-user-data.component.ts` and the analyzer dialog import a toast service in the whole dashboard feature.)
**Impact:** High (retention).
**Fix:** Fire a celebratory toast/animation when the user closes their rings or logs all three trackers — e.g. "Day logged — streak now 13 🔥". Reuse the existing streak signal so the reward names the streak.

**Finding:** The streak-at-risk strip (`dashboard.component.html:40-45`) is excellent — a full-width amber banner "Your 12-day streak is at risk — log today's data before midnight!" But it only renders when the user is *already on the dashboard*. The person who needs it is the one who hasn't opened the app.
**Impact:** High — see Retention.

### 3. Social Layer UX & Cold Start

**Finding:** Cold-start is handled deliberately and well. A zero-follow user hitting the feed gets `app-social-feed-guided-empty` (`social-feed.component.html:45-54`), which inlines **suggested users with one-tap Follow buttons** (pending/following states, skeletons, error+retry) rather than a dead "no posts" screen. Discover, chat, and search all have converting empty states ("Find Athletes" → `/social/discover`). This is textbook empty-state-as-conversion.
**Impact:** Working well.

**Finding:** The like/comment/follow loop (`post-card.component.html:174-192`) is clean with optimistic like toggle and `aria-pressed`. But there is **no share / repost and no double-tap-to-like** — both are table-stakes gestures for the target user (Instagram/Strava muscle memory). Sharing is also the cheapest organic-growth lever and it's absent from the post card entirely (the feed header's "New" button is commented out, `social-feed.component.html:19-22`).
**Impact:** Medium.
**Fix:** Add double-tap-to-like on the post image and a share affordance (at minimum "share to a DM" using the existing conversation infra).

**Finding:** Notification triggers (`NotificationService.cs`) cover like / comment / follow / message — all **reactive social events**. There is no notification for any *fitness* event (streak milestone, streak-at-risk, a followed athlete logging a PR). The social graph is disconnected from the fitness graph in the one system designed to pull users back.
**Impact:** High — see Retention.

### 4. Mobile UX & Navigation Coherence

**Finding:** Mobile navigation is coherent but **split-brained across two independent nav systems**, and the CLAUDE.md description of `bottom-nav`/`top-bar` living under `features/social/components/` is stale — they actually live at app level (`shared/components/bottom-nav`, `shared/components/top-bar`). On mobile (≤768px) `social-shell` suppresses the desktop `side-nav` entirely (`social-shell.component.html:11`) and relies on the app-level `top-bar` + `bottom-nav`. The two navs expose **different destinations**:

| Destination | Desktop `side-nav` | Mobile `bottom-nav` |
|---|---|---|
| Feed | ✓ | ✓ (home) |
| Discover | ✓ | ✗ (only via top-bar search icon) |
| Chat | ✓ | ✓ |
| Notifications | ✓ | ✗ (only via top-bar bell) |
| Profile | ✓ | ✓ |
| Dashboard | ✗ ("Back to NovaFit" link) | ✓ (grid_view) |
| Create | "New" button | ✓ (center FAB) |

**Impact:** Medium.
**Fix:** This is defensible (Discover/Notifications demoted to the top-bar is an Instagram-style pattern) but the demotion of **Discover** hurts the cold-start user most — the primary follow-acquisition surface is a search magnifier they must discover. Consider surfacing Discover more prominently for zero-follow users, or swap it into the bottom-nav until the user follows N people.

**Finding:** Potential **floating-button pile-up on mobile social routes.** `social-shell` renders a `daily-panel-fab` whenever `isNarrow()` (≤1199px), which **includes** all mobile widths (`social-shell.component.html:36`). Yet the sibling comment in `app.component.ts:57` asserts "the daily-panel-fab is desktop-only after this redesign." On a ≤768px social route you can therefore stack: bottom-nav center Create FAB + `app-ai-chat-fab` + `daily-panel-fab`. The code's own stated intent (mobile offset always 0) contradicts what the template renders.
**Impact:** Medium.
**Fix:** Gate `daily-panel-fab` on a desktop/tablet-only breakpoint (e.g. 768–1199px), not `isNarrow()`, to match the documented intent and avoid overlapping the bottom-nav.

**Finding:** Badge sources are inconsistent between navs. `bottom-nav` computes unread messages by summing `conversations().unreadCount` locally (`app-bottom-nav.component.ts:20`), while `side-nav` is fed `chatFacade.unreadConversationsCount()`. Same for notifications (side-nav has a notif badge; bottom-nav has none — it lives on the top-bar bell). Two code paths for the same number will drift.
**Impact:** Low.
**Fix:** Single source of truth for unread counts consumed by both navs.

### 5. Retention Mechanics

**Finding:** In-app retention scaffolding is strong: server-computed streak (single source of truth, `DailyDataService.GetStreakAsync`, delegated to by `DashboardService.cs:93`), `current` + `longest` + `atRisk` + `loggedToday` signals, an animated streak chip, a `streak-badge` in the social nav, and the at-risk banner. The pieces are all here.
**Impact:** Working well (in-app).

**Finding — the central gap:** **There is zero outbound re-engagement.** All notifications are in-app only (SignalR push + stored), and every trigger is a reactive social event (like/comment/follow/message). Nothing emails or pushes a lapsing user. The at-risk streak — the single most powerful re-engagement hook the app already computes — is only visible to users who *return on their own*. MailKit/Gmail SMTP is already wired for transactional email, so the delivery channel exists and is unused for retention.
**Impact:** Critical.
**Fix:** Add a scheduled job that, for users who haven't logged today and whose streak `atRisk` is true, sends an evening "Log today to keep your {N}-day streak 🔥" email (and/or web-push). This reuses existing streak logic + existing email infra — no new subsystems.

**Finding:** No streak-milestone reward. Hitting 7 / 30 / 100 days produces nothing (no notification, badge, or shareable card). Milestones are the cheapest viral + retention moment and are unbuilt.
**Impact:** Medium.
**Fix:** On milestone days, fire a celebratory notification + offer a one-tap "share my 30-day streak" post into the existing feed.

## Top 5 Priority Fixes

| Rank | What's Broken | The Fix | Retention Impact | Effort |
|------|--------------|---------|-----------------|--------|
| 1 | No outbound re-engagement; at-risk streak only visible in-app | Scheduled evening reminder (email via existing MailKit / web-push) for un-logged users with `atRisk` streak | High | M |
| 2 | Daily loop has no reward/closing beat — completion = silent 16px icon | Celebratory toast/animation on ring-close or full daily log, naming the streak | High | S |
| 3 | Social notifications never reflect fitness events (streak milestones, at-risk) | Add streak-milestone + at-risk notification types to existing NotificationService | High | M |
| 4 | Discover (primary follow-acquisition surface) demoted to a search icon on mobile | Surface Discover in bottom-nav (or prominently in feed) for zero-follow users | Med | S |
| 5 | `improve_fitness` goal silently maps to `maintain`, corrupting personalized numbers | Remove the option or give it a distinct calorie strategy | Med | S |

**Also fix (polish):** mobile FAB pile-up (`daily-panel-fab` shows ≤768px against its own documented intent); unused `dietaryPreference`; `your-numbers` skip uses `href` not `routerLink`; disabled buttons carry Romanian tooltip text ("Disponibil în curând") in an otherwise-English UI (login/register social + forgot-password); no share/double-tap-to-like on posts.

---

## Final Verdict

**Onboarding, the daily loop, and social cold-start are production-ready** — they show real craft (live TDEE, numbers reveal, guided empty states, undo, auto-save). The module that is **not** ready to support user growth is **retention**: the app builds a beautiful streak and then never uses it to bring anyone back. Every retention mechanism is passive and in-app. Ship the onboarding and daily loop as-is; do **not** count on organic retention until at least Priority Fixes 1–3 (outbound reminder, reward beat, fitness-event notifications) are built. The infrastructure to do all three — streak logic, MailKit email, SignalR, NotificationService — already exists; this is wiring, not new architecture.
